구조 — 요청은 이렇게 흐릅니다

Claude Code는 Anthropic API 서버 대신 내 컴퓨터의 LiteLLM에 말을 겁니다. LiteLLM은 요청을 로컬 브리지로 넘기고, 브리지가 Microsoft Copilot SDK(구 GitHub Copilot SDK)를 통해 Gemini 4를 호출합니다. 세 프로세스 모두 노트북 안(127.0.0.1)에서 돕니다.

  • LiteLLM이 하는 일. 모델 별칭 4개(gemini-4-argon … gemini-4-neon)를 받아 같은 이름으로 브리지에 넘기고, 마스터 키로 인증하고, 요청마다 로그를 남깁니다(STEP 6의 gemini-litellm logs). 브리지의 토큰은 LiteLLM만 알고, Claude Code는 LiteLLM의 키만 가집니다.
  • 설정은 건드리지 않습니다. claude-gemini-litellm 은 실행할 때마다 설정 파일(권한 600, LiteLLM 키 포함)을 만들어 --settings 로 넘깁니다. print 모드(-p)는 끝나면 바로 지우고, 대화형은 gemini-litellm down 이 지웁니다. ~/.claude/settings.json 은 그대로입니다.
  • 별칭에는 claude- 도 [1m] 도 붙지 않습니다. LiteLLM 경로에서는 /model 목록(modelPicker)을 설정 파일에 직접 적기 때문에 모델 이름이 gemini-4-neon 그대로입니다. 대신 Claude Code가 모르는 이름이라 컨텍스트 창을 1M 토큰으로 가정한다는 안내가 한 줄 뜹니다(Gemini 4의 실제 창과 같아서 그대로 둡니다).
  • Claude Code 안의 별칭도 Gemini 4로 고정됩니다. opus→Neon, sonnet→Carbon, haiku→Hydrogen (카탈로그 단가 순서일 뿐 성능 순위가 아닙니다). Claude Code가 알아서 보내는 작은 요청도 Gemini 4 밖으로 나가지 않습니다.
  • LiteLLM은 두 가지를 꼭 켜 둡니다. ① forward_client_headers_to_llm_api — 세션·서브에이전트 ID 헤더를 브리지까지 전달해야 대화를 구분합니다. ② 모델별 model_info — 없으면 LiteLLM이 Claude Code의 추론 강도(effort) 설정을 버립니다. 설정은 examples/litellm-gemini.yaml 에 있습니다.

STEP 1설치 — 의존성과 LiteLLM

저장소를 내려받고 의존성을 설치하고, LiteLLM을 이 저장소 안(.runtime/, git 제외)에 한 번 설치하고, 이 터미널에서 명령들을 바로 쓸 수 있게 합니다.

이미 LiteLLM을 쓰고 있다면

아래 gemini-litellm setup 줄만 건너뜁니다(저장소를 받고 의존성을 설치하는 것은 그대로). LiteLLM은 새로 설치하지 않고 내 LiteLLM에 연결합니다.

터미널
git clone {{repo-url}}   # 처음 한 번만
cd {{repo-name}}
npm ci

이렇게 되면 성공
  • npm ci 가 오류 없이 끝납니다 (Copilot SDK {{sdk-version}} 고정).
  • command -v claude-gemini-litellm 이 이 저장소의 bin/claude-gemini-litellm 경로를 출력합니다.
  • gemini-litellm setup 가 is ready 로 끝나고, 같은 명령을 다시 실행해도 안전합니다(이미 설치돼 있으면 건너뜁니다).

그래서 설치기는 버전을 고정하고(litellm=={{litellm-version}}), 플랫폼별 SHA-256 해시가 다르면 설치를 거부합니다(pip --require-hashes). 패키지 저장소는 pip 설정을 그대로 따르므로, 사내 미러를 쓰는 환경에서도 같은 명령으로 됩니다.

claude 명령은 바꾸지 않습니다. Gemini 4로 실행할 때만 claude-gemini-litellm 을 쓰고, 평소의 claude 는 그대로입니다.

STEP 3게이트웨이 시작 — 브리지와 LiteLLM 켜기

한 명령으로 브리지와 그 앞의 LiteLLM을 켭니다. 게이트웨이는 백그라운드에서 계속 돌고, Claude Code는 이 주소(127.0.0.1:4000)로 접속합니다.

이미 LiteLLM을 쓰고 있다면 이 단계를 건너뛰세요

gemini-litellm up 은 이 저장소가 설치한 LiteLLM만 켭니다. 내 LiteLLM에는 바로 다음 절 기존 LiteLLM에 연결하기가 이 단계를 대신합니다.

터미널
gemini-litellm up        # 브리지 → LiteLLM 순서로 시작 (10초 안팎)
gemini-litellm status    # 상태 확인

LiteLLM이 읽는 설정은 이 저장소의 examples/litellm-gemini.yaml 입니다. 별칭 하나는 이런 모양이고, 나머지 3개도 같습니다.

examples/litellm-gemini.yaml (일부)
model_list:
  - model_name: gemini-4-neon                 # Claude Code가 부르는 별칭
    litellm_params:
      model: anthropic/gemini-4-neon          # 브리지로 보낼 때의 모델 ID
      api_base: os.environ/GHCP_BRIDGE_URL    # 브리지 주소 (gemini-litellm up 이 넣어 줌)
      extra_headers:                          # 토큰은 api_key 가 아닌 헤더로 (이유는 아래)
        x-api-key: os.environ/GHCP_BRIDGE_TOKEN
general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  forward_client_headers_to_llm_api: true     # 세션·서브에이전트 ID 헤더를 브리지까지 전달
토큰을 api_key 에 넣지 않은 이유 — 대화가 Anthropic으로 나갈 수 있습니다

LiteLLM은 anthropic/ 경로에 api_key 가 있으면, Claude Code가 보내는 토큰 수 계산 요청(/v1/messages/count_tokens)을 설정한 브리지가 아니라 api.anthropic.com 으로 보냅니다. 대화 전체와 그 키가 함께 나갑니다. 그래서 이 설정은 토큰을 헤더로만 보내고 api_key 를 두지 않습니다. 그러면 LiteLLM이 안에서 추정값으로 답하고 아무것도 밖으로 나가지 않습니다. 이 파일을 고칠 때 api_key 를 추가하지 마세요(단위 테스트와 검증 시나리오가 확인합니다).

포트가 이미 쓰이고 있으면

LiteLLM 기본 포트는 4000 입니다. 다른 프로그램이 쓰고 있으면 gemini-litellm up --port 4100 으로 바꾸고, 이후 Claude Code 쪽은 --litellm-base-url http://127.0.0.1:4100 을 붙입니다.

STEP 3 대신기존 LiteLLM에 연결하기

이미 쓰는 LiteLLM(직접 실행 · Docker · 서버)이 있으면 새로 설치할 필요가 없습니다. 내 LiteLLM에 Gemini 4 별칭 4개를 더하고, 브리지를 따로 켜 두면 됩니다. 순서는 STEP 1(gemini-litellm setup 줄만 빼고) → STEP 2(--litellm 없이) → 이 절 → STEP 4~9 입니다. 달라지는 점은 해당 단계에 적어 두었습니다.

STEP 3 에서 gemini-litellm up 을 이미 했다면 이 절은 건너뛰세요

이 저장소의 LiteLLM을 켠 독자는 바로 STEP 4 로 갑니다. 이 절은 이미 쓰는 LiteLLM이 있는 독자가 STEP 3 대신 따라 하는 길입니다.

① 브리지를 포트와 토큰을 정해서 켜기

gemini-litellm up 이 켜는 브리지는 켤 때마다 새 토큰을 받는데, 이미 떠 있는 내 LiteLLM은 그 토큰을 알 수 없습니다. 그래서 포트와 토큰을 직접 정해 브리지를 켭니다. 토큰은 처음 한 번만 만들고, 브리지를 다시 켤 때는 같은 값을 export BRIDGE_API_KEY=… 로 쓰면 LiteLLM 설정을 고칠 일이 없습니다.

터미널 A — 브리지 (계속 켜 두는 터미널)
export BRIDGE_API_KEY=$(openssl rand -hex 24)   # 브리지 토큰 만들기 (처음 한 번만)
echo "$BRIDGE_API_KEY"        # 이 값을 ②·③ 에서 LiteLLM에 알려 줍니다 — 따로 적어 두세요
unset COPILOT_CLI_PATH        # Copilot CLI 세션 안에서 열었다면
PORT=4142 npm run bridge      # 브리지 시작 · 끌 때는 Ctrl-C
터미널 B
curl -s http://127.0.0.1:4142/health   # "ok":true 가 보이면 떠 있는 것 (토큰 없이도 답합니다)
이렇게 되면 성공
  • 터미널 A에 {"event":"bridge.started","address":"http://127.0.0.1:4142", …} 한 줄이 나옵니다.
  • 터미널 B의 curl 이 "ok":true 를 돌려줍니다.
백그라운드로 두려면

PORT=4142 nohup npm run bridge > /tmp/gemini-bridge.log 2>&1 & 로 켜고 kill 로 끕니다. 부팅 때 자동으로 켜려면 같은 명령을 launchd · systemd · pm2 같은 프로세스 관리자에 등록하세요(이 가이드는 검증하지 않았습니다).

② 내 LiteLLM에 모델 4개 더하기

기존 모델과 설정은 그대로 두고 덧붙입니다. examples/litellm-gemini.yaml 과 같은 내용이고, 브리지 주소를 ①의 고정 주소로 적은 것과 헤더 전달을 이 4개 모델에만 켠 것이 다릅니다. 모델을 설정 파일로 관리하면 A, UI · API(DB)로 관리하면 B 로 모델을 더하고, 헤더 전달 설정 C 는 둘 다 합니다.

A. 설정 파일(config.yaml)로 모델을 관리한다면

config.yaml 에 덧붙일 것 — 모델
model_list:
  # ... 기존 모델은 그대로 두고, 아래 4개를 덧붙입니다 ...
  - model_name: gemini-4-argon                    # Claude Code가 부르는 별칭
    litellm_params:
      model: anthropic/gemini-4-argon             # 브리지로 보낼 때의 모델 ID
      api_base: http://127.0.0.1:4142             # 브리지 주소 (/v1 은 붙이지 않습니다)
      extra_headers:
        x-api-key: os.environ/GHCP_BRIDGE_TOKEN   # 브리지 토큰은 api_key 가 아닌 헤더로
    model_info: &effort_passthrough               # 없으면 effort 가 버려짐
      supports_adaptive_thinking: true
      supports_xhigh_reasoning_effort: true
  - model_name: gemini-4-carbon
    litellm_params:
      model: anthropic/gemini-4-carbon
      api_base: http://127.0.0.1:4142
      extra_headers:
        x-api-key: os.environ/GHCP_BRIDGE_TOKEN
    model_info: *effort_passthrough
  - model_name: gemini-4-hydrogen
    litellm_params:
      model: anthropic/gemini-4-hydrogen
      api_base: http://127.0.0.1:4142
      extra_headers:
        x-api-key: os.environ/GHCP_BRIDGE_TOKEN
    model_info: *effort_passthrough
  - model_name: gemini-4-neon
    litellm_params:
      model: anthropic/gemini-4-neon
      api_base: http://127.0.0.1:4142
      extra_headers:
        x-api-key: os.environ/GHCP_BRIDGE_TOKEN
    model_info: *effort_passthrough

B. UI · API(DB)로 모델을 관리한다면 (STORE_MODEL_IN_DB) — 같은 값을 /model/new API로 넣습니다. api_key 는 비웁니다. 단 DB에 저장된 모델은 extra_headers 안의 os.environ/… 를 치환하지 않으므로(1.111.0 에서 확인) 토큰 값을 그대로 넣어야 하고, 그 토큰은 LiteLLM의 DB에 저장됩니다. UI의 모델 추가 화면에서 넣을 때도 같은 값을 쓰지만, UI는 확인하지 않았습니다.

터미널 B — 모델 4개를 API로 더하기
export LITELLM_BASE_URL=http://127.0.0.1:4000     # 내 LiteLLM 주소
ADMIN_KEY=sk-...  BRIDGE_API_KEY=...              # 관리자(마스터) 키 · ①의 토큰
BRIDGE_URL=http://127.0.0.1:4142                  # Docker 안이면 host.docker.internal
for id in gemini-4-argon gemini-4-carbon gemini-4-hydrogen gemini-4-neon; do
  curl -s -o /dev/null -w "$id %{http_code}\n" "$LITELLM_BASE_URL/model/new" -H "Authorization: Bearer $ADMIN_KEY" -H "content-type: application/json" -d @- <<EOF
{"model_name": "$id",
 "litellm_params": {"model": "anthropic/$id", "api_base": "$BRIDGE_URL",
                    "extra_headers": {"x-api-key": "$BRIDGE_API_KEY"}},
 "model_info": {"supports_adaptive_thinking": true, "supports_xhigh_reasoning_effort": true}}
EOF
done

각 줄이 gemini-4-… 200 이면 모델이 더해진 것입니다(바로 적용되고 LiteLLM을 다시 시작하지 않아도 됩니다).

C. 헤더 전달 설정 (A · B 공통) — 모델을 어떻게 더했든 config.yaml 에 덧붙입니다.

config.yaml 에 덧붙일 것 — 헤더 전달
litellm_settings:                                 # 이미 있으면 그 안에 추가
  model_group_settings:
    forward_client_headers_to_llm_api:            # 이 4개에만 헤더 전달
      - gemini-4-argon
      - gemini-4-carbon
      - gemini-4-hydrogen
      - gemini-4-neon
  • api_base 는 브리지 주소입니다. 내 LiteLLM이 Docker 안이면 127.0.0.1 이 컨테이너 자신이라 닿지 않습니다(③).
  • A 에서 쓰는 GHCP_BRIDGE_TOKEN 은 LiteLLM 프로세스의 환경 변수로 ①의 토큰을 넘깁니다(③). 설정 파일에 토큰을 적지 않아도 됩니다.
  • model_group_settings 는 x-claude-code-session-id · x-claude-code-agent-id 헤더를 브리지까지 전달합니다. 없으면 브리지가 대화와 서브에이전트를 구분하지 못해, 모든 요청을 한 대화처럼 한 번에 하나씩 처리합니다. UI로는 만들 수 없어 config.yaml 에 두며, DB 모델에도 적용됩니다(확인함).
  • 왜 4개에만 켤까요? 저장소의 예시 파일처럼 general_settings.forward_client_headers_to_llm_api: true 로 켜면 내 LiteLLM의 모든 모델 업스트림에 클라이언트가 보낸 x- 헤더가 전달됩니다(확인함: 기존 모델의 업스트림이 x-claude-code-session-id 를 받았습니다). 이미 전역으로 켜 둔 LiteLLM이면 그대로 두어도 동작하고, 이 설정을 모르는 오래된 LiteLLM은 전역 설정을 쓰세요(LiteLLM 문서).
이 4개 모델에 Anthropic 키가 닿으면 안 됩니다 — api_key 도, 환경 변수 ANTHROPIC_API_KEY 도

Claude Code가 보내는 토큰 수 계산 요청(/v1/messages/count_tokens)을 LiteLLM은 anthropic/ 모델이면 Anthropic 방식으로 처리하며, 키는 배포의 api_key, 없으면 LiteLLM 환경의 ANTHROPIC_API_KEY 를 씁니다. 진짜 Claude 모델도 쓰는 LiteLLM이라면 그 변수가 있을 수 있습니다. (모델 호출 자체는 extra_headers 의 토큰이 우선해서 정상입니다.)

  • LiteLLM 1.97.0 (이 저장소 고정 버전)은 api.anthropic.com 으로 보냅니다 — 대화 전체와 그 키가 함께. 키가 있을 때 api.anthropic.com:443 으로 연결을 시도하는 것을 확인했습니다(실제 전송은 막고 관찰).
  • LiteLLM 1.111.0 (Docker main-stable, 2026-11-25)은 배포의 api_base, 곧 브리지로 보냅니다. Anthropic으로 나가지는 않지만 그 키가 브리지로 전달되고 401 이 납니다.
  • 키가 없으면 1.97.0 은 LiteLLM 안에서 추정값으로 답하고 1.111.0 은 401 로 답합니다. 어느 쪽이든 Claude Code는 자체 추정으로 계속 동작합니다(/context 로 확인).

확인 docker exec <컨테이너> printenv ANTHROPIC_API_KEY (직접 실행이면 env | grep ANTHROPIC), compose · .env · 설정의 environment_variables.
조치 변수 이름을 바꾸고(예 MY_ANTHROPIC_KEY) 내 Claude 배포에 api_key: os.environ/MY_ANTHROPIC_KEY 를 명시한 뒤 LiteLLM을 다시 시작합니다. 바꿀 수 없다면 이 저장소의 게이트웨이를 gemini-litellm up --port 4100 으로 따로 켜서 쓰세요(이쪽은 ANTHROPIC_ 환경 변수를 비우고 시작합니다).

같은 이름의 모델이 이미 있다면

LiteLLM은 model_name 이 같은 항목을 한 그룹으로 묶어 번갈아 호출합니다. 내 LiteLLM에 gemini-4-… 라는 이름이 이미 있으면 별칭만 바꾸세요(예 ghcp-gemini-4-neon). model: anthropic/gemini-4-neon 은 그대로 두고, model_group_settings 목록에도 새 이름을 적고, Claude Code에서는 --litellm-model ghcp-gemini-4-neon 으로 고릅니다(확인함).

③ 내 LiteLLM 다시 시작

LiteLLM은 설정 파일과 환경 변수를 시작할 때 한 번 읽습니다. config.yaml 을 고쳤으니 다시 시작하세요. A 는 ①의 토큰을 환경 변수 GHCP_BRIDGE_TOKEN 으로 함께 넘깁니다(B 는 토큰이 DB에 들어 있어 필요 없습니다).

직접 실행하는 LiteLLM
GHCP_BRIDGE_TOKEN=<①의 토큰> litellm --config config.yaml --port 4000
LiteLLM이 Docker 안에 있다면
  • 컨테이너 안의 127.0.0.1 은 컨테이너 자신입니다. ②의 api_base 를 http://host.docker.internal:4142 로 적으세요. 호스트의 127.0.0.1 에만 열린 브리지에 닿는 것을 macOS의 Colima 에서 확인했습니다(Docker Desktop도 같은 이름을 제공하지만 확인하지 않았습니다).
  • GHCP_BRIDGE_TOKEN 은 docker run -e GHCP_BRIDGE_TOKEN=… 나 compose의 environment: 로 넘깁니다. 환경 변수가 바뀌면 docker restart 가 아니라 컨테이너를 다시 만드세요(docker compose up -d).
  • Linux의 Docker는 host.docker.internal 이 기본으로 없고 호스트의 127.0.0.1 에도 닿지 않아 추가 설정이 필요합니다(검증하지 않음).

④ Claude Code를 내 LiteLLM에 연결

런처는 주소를 LITELLM_BASE_URL, 키를 LITELLM_API_KEY 에서 읽습니다. 터미널에 한 번 export 해 두면 STEP 4~9 의 명령을 그대로 쓸 수 있습니다.

터미널 B
export LITELLM_BASE_URL=http://127.0.0.1:4000   # 내 LiteLLM 주소 (/v1 없이)
export LITELLM_API_KEY=sk-...                   # 내 LiteLLM에서 받은 키
gemini-doctor                                   # STEP 2 점검 (--litellm 없이)
claude-gemini-litellm --litellm-model gemini-4-hydrogen -p "한국의 수도는 어디인가요? 한 단어로만 답해줘."
  • 다른 서버의 LiteLLM이면 LITELLM_BASE_URL 에 https://litellm.example.com 처럼 적습니다(런처는 http · https 를 모두 받고, 끝에 /v1 을 붙이면 거절합니다).
  • LITELLM_API_KEY 는 꼭 직접 지정하세요. 주소가 127.0.0.1 · localhost 인데 키를 비워 두면 런처가 이 저장소의 .runtime/litellm-master-key 를 읽어, 내 LiteLLM에서 LiteLLM rejected the key. 가 납니다(DB 없이 마스터 키만 쓰는 LiteLLM은 다른 키에 400 No connected db. 로 답해서 LiteLLM answered 400 to GET /v1/models. 가 납니다).
  • 마스터 키 대신 이 4개 별칭만 허용한 가상 키를 쓰세요(POST /key/generate 의 "models": ["gemini-4-argon", …]). 가상 키로 확인했습니다: /v1/models 에는 허용한 별칭만 보이고, 허용하지 않은 별칭을 고르면 런처가 LiteLLM does not serve … 로 알려 줍니다.
  • 대화형으로 열면 런처가 LiteLLM 키가 든 설정 파일(권한 600)을 .runtime/settings/ 에 남깁니다. 다 쓴 뒤 gemini-litellm down 을 실행하면 그 파일만 지웁니다. 이 저장소가 켠 게이트웨이가 없으면 두 줄 모두 was not running 이라고만 나오고, 내 LiteLLM은 건드리지 않습니다.
이렇게 보이면 성공
  • curl -s "$LITELLM_BASE_URL/v1/models" -H "Authorization: Bearer $LITELLM_API_KEY" 에 gemini-4-argon … gemini-4-neon 이 보입니다(가상 키면 허용한 것만).
  • -p 호출이 서울 같은 답을 냅니다. 노란 Claude Code doesn't recognize the model… 안내는 STEP 4 와 같은 정상 안내입니다.
  • 터미널 A(브리지)에 "event":"bridge.turn_completed" 줄이 찍히고 requestedModel 과 model 이 같습니다 → 요청이 내 LiteLLM을 지나 그 Gemini 4 모델이 처리했습니다.
여기까지 되면 STEP 4 로 이어가세요

④에서 첫 호출을 이미 해 봤으니 STEP 4 는 “4개 모델에 같은 질문 던져 보기”부터 하면 됩니다. LITELLM_BASE_URL · LITELLM_API_KEY 를 export 한 같은 터미널에서 STEP 4~9 의 명령을 그대로 쓰세요(STEP 4 의 두 명령이 그대로 동작하는 것을 확인했습니다).

STEP 6 의 gemini-litellm turns · logs 는 이 저장소가 켠 게이트웨이용이라 여기서는 쓸 수 없습니다. 요청 로그는 내 LiteLLM에서(예 docker logs), 브리지가 처리한 턴은 터미널 A에서 봅니다. 막히면 문제 해결 표의 Invalid bridge credential · Cannot connect to host 항목을 보세요.

내 LiteLLM이 다른 서버에 있다면

브리지는 기본으로 127.0.0.1 에만 열립니다(ALLOW_NON_LOOPBACK=1 없이는 다른 주소로 열리지 않습니다). 다른 서버의 LiteLLM이 닿으려면 브리지를 그 서버에서 실행하세요(그 서버에서 copilot login). 알아 둘 점: 브리지는 실행한 계정의 Copilot 으로 호출하므로, 그 LiteLLM을 쓰는 모든 사람의 요청이 그 한 계정의 사용량으로 잡힙니다. 이 구성은 검증하지 않았습니다.

확인한 범위. 이 절은 LiteLLM 1.97.0(pip)과 1.111.0(Docker main-stable, 2026-11-25)에서 실제 Gemini 4 호출로 확인했습니다 — 설정 파일 모델, API로 더한 DB 모델, 가상 키. npm run verify:litellm 에는 포함되지 않았고, 다른 버전은 위 경고(토큰 수 계산)와 model_group_settings 지원 여부부터 확인하세요.

STEP 4첫 호출 — 한 번 묻고 끝내기

표의 값은 “요청 → 실제 SDK 세션에 적용된 값”입니다. SDK 런타임({{runtime-version}})은 네 모델 모두 xhigh 를 “지원하지 않는 추론 강도” 오류로 거부하므로, 브리지가 high 로 낮춰 적용합니다. 그래서 Claude Code 설정에 effortLevel: "xhigh" 가 있어도 요청이 실패하지 않습니다. (카탈로그에는 Hydrogen·Neon 의 옛 항목에 xhigh 가 남아 있지만, 이 저장소는 런타임이 검사하는 최상위 목록 low · medium · high 를 기준으로 판단합니다.)

LiteLLM이 effort를 버리지 않게 하는 설정

LiteLLM은 anthropic/ 경로 뒤의 모델이 Gemini 4라는 것을 몰라서, 따로 알려 주지 않으면 Claude Code가 보낸 추론 설정(output_config.effort)을 “Dropping adaptive thinking/output_config.effort” 경고와 함께 버립니다. examples/litellm-gemini.yaml 의 모델별 model_info(supports_adaptive_thinking · supports_xhigh_reasoning_effort)가 그것을 막아, 위 표처럼 effort가 브리지까지 도착합니다.

  • 비공식 구성입니다. Anthropic은 Claude가 아닌 모델을 게이트웨이로 연결하는 구성을, GitHub은 이 조합을 지원하지 않으며, 이 저장소의 LiteLLM 설정도 LiteLLM이 보증하는 구성이 아닙니다. 개인 실험·연구용으로 쓰세요.
  • STEP 3 의 LiteLLM은 이 노트북 안에서만 쓰는 구성입니다(127.0.0.1). 이미 쓰는 LiteLLM에 연결하는 방법은 따로 있습니다. 다른 사람과 게이트웨이를 공유하려면 가상 키·네트워크 보안·로그 보관을 따로 설계해야 합니다. 이 가이드는 그 부분을 검증하지 않았습니다.
  • 기존 LiteLLM 연결은 수동으로 확인한 범위입니다: LiteLLM 1.97.0 · 1.111.0, 설정 파일 모델 · API로 더한 DB 모델 · 가상 키, 실제 Gemini 4 호출. npm run verify:litellm 에는 포함되지 않았고, UI 화면 · 원격 LiteLLM · 여럿이 공유하는 구성 · 다른 버전은 검증하지 않았습니다.
  • 금액·예산 기능은 의미가 없습니다. Gemini 4는 GitHub Copilot 구독으로 처리되고, LiteLLM과 Claude Code는 이 모델들의 단가를 모릅니다. /cost 나 LiteLLM의 지출 집계 숫자를 믿지 마세요. 실제 사용량은 GitHub Copilot 쪽에서 봅니다.
  • Claude Code가 보내는 토큰 수 사전 계산(count_tokens) 요청은 LiteLLM이 Anthropic에 묻지 않고 자체 추정값으로 답합니다. 실제 Gemini 4 토큰 수와는 다를 수 있습니다. (이미 쓰는 LiteLLM에 연결하면 버전과 환경 변수에 따라 달라집니다 — 기존 LiteLLM에 연결하기의 경고를 보세요.)
  • Claude Code의 확장 사고(thinking) 블록은 표시되지 않습니다. 대신 추론 강도(effort)가 전달됩니다.
  • temperature·top_p·stop_sequences 같은 샘플링 제어와 cache_control 표시는 적용되지 않습니다.
  • WebSearch 처럼 Anthropic 서버에서 실행되는 기능은 쓸 수 없습니다.
  • 모델을 바꾸면 새 모델이 대화 전체를 다시 읽습니다 (Claude Code 확인창의 경고 그대로).
  • 서브에이전트(Explore 등)는 시작할 때 고른 모델로 실행되는 것을 검증했습니다. 도중에 /model 로 바꾼 뒤의 서브에이전트 동작은 검증하지 않았습니다.
